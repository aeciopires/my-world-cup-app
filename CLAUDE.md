# CLAUDE.md

Guidance for Claude Code (and other contributors) working in this repository.

## Project Summary

My World Cup App is a Go web application displaying FIFA World Cup 2026 group standings, knockout stage results, and match data, plus links to official FIFA resources. It has no database: tournament data is fetched live from [openfootball/worldcup.json](https://github.com/openfootball/worldcup.json) on startup and on demand, cached in memory.

Full details: see `README.md` (architecture, stack, directory structure, Mermaid diagram), `REQUIREMENTS.md` (supported platforms + toolchain), `docs/` (beginner's guide with analogies and Mermaid diagrams), and `PLANS/PLAN.md` / `PLANS/TASK.md` / `PLANS/TASK2.md` (original and follow-up requirements).

## Conventions

- **Language**: all code, comments, commit messages, and documentation must be in **en-US**, regardless of the language used in requests.
- **No web framework**: use Go's standard library (`net/http`, `html/template`) only for routing/rendering. This constraint applies to the web layer specifically, not to observability tooling — `prometheus/client_golang` (`app/internal/metrics`) and OpenTelemetry (`go.opentelemetry.io/otel`, its SDK, the OTLP/HTTP trace exporter, and `otelhttp`; `app/internal/telemetry`) are intentional, discussed exceptions. Do not add further dependencies (router, template library, etc.) without discussing it first.
- **Use the `modern-go-guidelines` skill for all Go work**: whenever you create, modify, review/analyze, or test Go code in this repo (`app/**/*.go`, including `_test.go` files), first invoke the `use-modern-go` skill from the `modern-go-guidelines` plugin (`modern-go-guidelines:use-modern-go`) and follow the idioms it lists for the module's Go version. If the plugin isn't installed, install it with `claude plugin marketplace add JetBrains/go-modern-guidelines` then `claude plugin install modern-go-guidelines@goland-claude-marketplace`. When reviewing, flag pre-modern idioms (`sort.Slice`, manual `wg.Add`/`Done`, `context.Background()` in tests, hand-rolled min/max/map-key loops, `err ==` comparisons) as findings.
- **Modern Go**: the module targets Go 1.27 (`app/go.mod`). Write code per the [JetBrains Modern Go Guidelines](https://github.com/JetBrains/go-modern-guidelines) (installed as the `modern-go-guidelines` Claude Code plugin; its `use-modern-go` skill lists the applicable idioms for the module's Go version): `slices`/`maps`/`cmp` over `sort`, `cmp.Or`, built-in `min`/`max`, `wg.Go`, `t.Context()`, `new(expr)`, `errors.Is`, etc. `make lint` (golangci-lint v2, `app/.golangci.yml`) runs the `modernize` analyzer and must stay at 0 issues.
- **No database**: tournament data lives only in the in-memory `data.Store` (`app/internal/data/store.go`). Don't introduce persistence without a clear reason.
- **Clean architecture layering**: `handlers` → `services` → `models`; `data` is a separate concern owning fetch/parse/cache. Handlers should not contain business logic (standings math, sorting rules); that belongs in `services`.
- **Standings/knockout/stats logic is pure**: `app/internal/services` functions take a `models.Tournament` and return computed values with no I/O — keep them that way so they stay trivially testable. The tournament is a **shared, read-only snapshot** (every concurrent request gets the same slices): never sort or mutate `t.Matches`/`t.Teams` in place — `slices.Clone` first, or build a fresh slice (see `filterMatches` in `services/matches.go`). Every sort over map-collected data needs a final tie-break that is unique (team name; player name + team), since map iteration order is random. `TeamStandings` (in `stats.go`) reuses the same `accumulateResult`/`collectStandings`/`sortStandings` helpers as `GroupStandings` (in `standings.go`) rather than duplicating the scoring math — extend those shared helpers instead of copy-pasting if you add another aggregation view.
- **Metrics**: `app/internal/metrics` owns a dedicated `prometheus.Registry` (not the global default). `metrics.RecordRefresh(err)` must be called at every `store.Refresh(ctx)` call site (`app/cmd/server/main.go`'s startup goroutine, `app/internal/handlers/refresh.go`) — if you add another refresh trigger, call it there too (but skip it for `data.ErrRefreshInProgress`, which isn't an attempt). `metrics.ObserveRequest` and the per-request access log are wired in automatically via `observeMiddleware` in `app/internal/handlers/router.go`, which must wrap the `ServeMux` directly (the mux sets `r.Pattern` on the request it receives). The `path` label is the route pattern; unmatched requests use `unmatchedRoute` (`"unmatched"`) — never the raw URL path, which would make label cardinality unbounded. `ObserveRequest(ctx, ...)` attaches the sampled trace ID as an exemplar; `/metrics` sets `EnableOpenMetrics: true` because exemplars only exist in the OpenMetrics format. Counter label combinations that must be visible before their first event (like `data_refresh_total{outcome}`) are pre-initialized in `init()` so `increase()` doesn't miss the first increment.
- **Logging**: logs are JSON by default (`LOG_FORMAT=json`; `text` is the alternative), built by `telemetry.NewLogger` (`app/internal/telemetry/log.go`), whose handler adds `trace_id`/`span_id` from the context. Always log with the `...Context(ctx, ...)` variants (`slog.InfoContext`, `WarnContext`, ...) when a request/refresh context exists, or the trace IDs are lost. Keep field names stable — the Grafana dashboards and the Alloy pipeline (`observability/`) parse them: `level`, `msg`, `route`, `status`, `duration_ms`, `trace_id`, `span_id`. Log `time.Duration` values as `.String()` (or a numeric `_ms` field), since slog's JSON handler would print raw nanoseconds.
- **Tracing**: OpenTelemetry, opt-in via the standard `OTEL_*` env vars — `telemetry.Setup` installs a real TracerProvider only when `OTEL_EXPORTER_OTLP_ENDPOINT`/`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` is set (and `OTEL_SDK_DISABLED` isn't true); the W3C propagator is always installed. `otelhttp.NewHandler` is the **outermost** middleware (`withMiddleware` in `router.go`), so recovered panics still land on the span as 500s; `observeMiddleware` renames the span to `METHOD route`. Probe/scrape paths (`untracedPaths`: `/healthz`, `/readyz`, `/metrics`) are never traced. Outgoing fetches use `otelhttp.NewTransport` (`data/client.go`), and `Store.Refresh` opens a `data.Refresh` span. `main.go` must keep flushing spans on exit (the deferred `shutdownTelemetry`). The binary's version comes from `-ldflags "-X main.version=..."` (Makefile `GO_LDFLAGS`, Dockerfile `APP_VERSION`) and is reported as `service.version`.
- **Health probes**: `/healthz` = liveness (always 200 while the process answers; never add dependency checks there — failing it restarts the pod) and `/readyz` = readiness (`handlers.Health`, 503 once `SetDraining()` is called on SIGTERM). Readiness intentionally ignores openfootball availability, since the embedded fallback keeps the app serving. `SHUTDOWN_DRAIN_DELAY` keeps serving after SIGTERM so load balancers notice the 503 first.
- **Data store**: `data.Store.Snapshot()` returns a `data.Snapshot` (`Tournament`, `LastUpdated`, `Source` = `data.SourceLive`/`data.SourceFallback`), read atomically. Page handlers take **one** snapshot per request and pass it to both the services and `newBaseData(snap, ...)`, so layout data (flags, links, "last updated") can't come from a different refresh than the page body. `Store.Refresh` uses `refreshMu.TryLock()`: only one refresh runs at a time and concurrent callers get `data.ErrRefreshInProgress` (`POST /refresh` maps it to `429` + `Retry-After`). `data.Client.Fetch` downloads the four files concurrently (`wg.Go`), caps each body at `maxSourceBytes` (10 MiB), and returns all failures via `errors.Join`.

## Working in this Repo

- Run `make check` (fmt-check + vet + lint + test) before considering a change done. Run `make check-deps` if you're unsure whether your machine has everything installed — it reports what's missing instead of failing mid-task; `make install-deps` installs it (both implemented in `scripts/deps.sh`, which must stay compatible with macOS's bash 3.2: no associative arrays/`mapfile`).
- **Toolchain via mise**: `mise.toml` is the single source of truth for tool versions (Go, golangci-lint, Helm, helm-docs, kind, kubectl). Every Makefile target invokes tools through `$(RUN)` (= `mise exec --` when mise is installed) — use `$(RUN)` in new targets too. Docker/Compose/Buildx are deliberately not managed (checked only). Supported dev platforms: Ubuntu 22.04/24.04/26.04 amd64, macOS amd64/arm64. When bumping a version, update `mise.toml`, `REQUIREMENTS.md`, and README's "Software Requirements" table together (for Go, also `app/go.mod` and the `Dockerfile` builder image).
- **Docs**: `docs/` is a beginner-oriented guide (analogies + Mermaid diagrams). If you change behavior it describes (routes, refresh flow, scoring rules, middleware, Make targets), update the matching chapter too.
- **Keep the Makefile and README.md in sync**: every `.PHONY` target in the `Makefile` must have a `## description` comment (used by `make help`) and a matching row in README.md's "Makefile Targets" table (`README.md#makefile-targets`). If you add, rename, or remove a target, update both. Same goes for the "Software Requirements" table if you add a new required tool, and the "Configuration" env var table (`README.md#configuration`) if you add/change an `app/internal/config` environment variable.
- The fork/branch/PR contribution workflow lives in `CONTRIBUTING.md`, not in this file — don't duplicate it here.
- New source JSON fields from openfootball should be added to the `raw*` structs in `app/internal/data/parser.go`, then mapped into `app/internal/models` — never expose the raw JSON structs outside the `data` package.
- The embedded fallback data lives in `app/internal/data/fallback/*.json` — a snapshot of the real openfootball 2026 files, embedded via `go:embed` so the app has content even with no network access. If the upstream schema changes, refresh this snapshot too.
- Templates live in `app/web/templates/`, embedded via `app/web/assets.go`. Every page template must `{{define "content"}}` and is rendered against `app/web/templates/layout.html`. Shared layout data comes from `handlers.baseData` (`app/internal/handlers/render.go`).
- Static assets (`app/web/static/css`, `app/web/static/js`) are embedded and served at `/static/*`; there is no build step (no bundler, no npm).
- **Team flags**: `baseData.Flags` (`app/internal/handlers/render.go`, built by `teamFlags()`) is a `map[string]string` of team name → flag emoji, populated from `Tournament.Teams` and available on every page. Any template showing a team name should render it as `<span class="team">{{flag $.Flags .TeamField}} {{.TeamField}}</span>` — use `$.Flags` (not `.Flags`) since `$` always refers to the root page data even inside nested `{{range}}` blocks. The `flag` template func (`app/internal/handlers/render.go`) wraps the emoji in a `<span class="flag">` chip (bordered, shadowed box — see `app/web/static/css/style.css`) so it reads as a small flag badge instead of a bare character; don't inline `{{index $.Flags ...}}` directly in markup anymore.
- **FIFA links for teams/stadiums/cities**: `baseData.TeamLinks`, `.StadiumLinks`, and `.CityLinks` (`app/internal/handlers/fifa_links.go`) are `map[string]string` keyed by team name, stadium name, and host city respectively, pointing at the matching official fifa.com page. The fifa.com slugs are looked up from manually maintained tables (`fifaTeamSlugs`, `fifaHostCitySlugs`, `fifaHostCountrySlugs`) since they don't always match the openfootball name or the stadium's own (sometimes sponsor-renamed) name — key stadium/host-city lookups off `Stadium.City`, not `Stadium.Name`. Render any of these with the `linked` template func, e.g. `{{linked $.TeamLinks .TeamField}}`, which falls back to plain text if no slug is mapped. **`models.Match.Ground` is the host city string** (e.g. `"Mexico City"`), **not the stadium name** (`"Estadio Azteca"`) — that's how every openfootball match fixture reports it. Always render a match's venue with `{{linked $.CityLinks .Ground}}`; `StadiumLinks` is keyed by stadium name and will silently never match `.Ground`, falling back to unlinked plain text.
- **Match scores**: render a match's outcome with the `result` template func, `{{result .}}` (on a `models.Match`). It shows the `FinalScore()` (after extra time when played) as a `<span class="score">` pill, plus an `a.e.t.` marker and `(pens x-y)` when applicable (`.result-note`), or `<span class="badge-scheduled">scheduled</span>` for unplayed matches. Don't render `.FullTime` directly — it's the 90-minute score and is wrong for matches decided in extra time. The lower-level `score` func (`{{score home away}}`) remains for a bare scoreline.
- **Scoring rules** (`app/internal/models/models.go`): openfootball's `et` score is **cumulative** (includes the first 90 minutes), so `Match.FinalScore()` returns `ExtraTime` when present, else `FullTime`. `Winner()` uses `FinalScore()` then penalties. `accumulateResult` uses `FinalScore()` (extra-time goals count; shoot-out kicks don't, so a match decided on penalties is a draw in team records). Goals carry `OwnGoal` (from `"owngoal": true`); they're listed under the benefiting team but scored by an opposing player, so `TopScorers` skips them.
- **Tables**: every `<table class="table">` must be wrapped in `<div class="table-responsive">...</div>` (see `app/web/static/css/style.css`) as a scroll fallback, but that scrollbar shouldn't normally trigger — `.table` deliberately does **not** set `min-width: max-content`, since that would force every column to its unwrapped width and defeat the `overflow-wrap`/`word-break` rules that let long cell content wrap instead. Give short, fixed-format values that would otherwise wrap character-by-character (dates, round names, group names) `class="nowrap-cell"`. Cells containing a team name (or two, for "Team1 vs Team2") should use `<td class="team-cell">` with the team(s) wrapped in `<span class="team">` as above, so the flag+name pair doesn't line-break. Below 640px, `.standings-table` (group tables) and `.matches-table` (fixture-list tables: home page, `/matches`, and each group's match-detail table) restack each row into a team-first block with the remaining fields shown as compact chips instead of scrolling (`@media (max-width: 640px)` in `app/web/static/css/style.css`) — every non-team `<td>` in one of these tables needs a `data-label="..."` attribute (e.g. `data-label="GD"`) for that stacked view to show a label.
- **Grid card widths**: `.group-grid` (Groups page) and `.home-grid` (Home page) size cards with `grid-template-columns: repeat(auto-fill, minmax(min(Npx, 100%), 1fr))` rather than a bare `minmax(Npx, 1fr)`. `auto-fill`/`auto-fit` only ever reduce the column *count*, never the minmax minimum itself, so an un-capped minimum still forces that width in a single narrow column and overflows the page on phones — wrap any new fixed minimum in `min(Npx, 100%)`. `.grid-2` (a plain `1fr 1fr`, used on `/stats`) is for side-by-side cards that don't carry long unbreakable text; the Home page intentionally uses full-width `.home-grid` cards instead of `.grid-2` so venue names have room to stay on one line at typical desktop widths.
- **Groups page expand/collapse-all**: each group's match results sit behind its own `<details class="group-matches">`. The "Expand all matches" / "Collapse all matches" button (`#toggle-all-matches` in `app/web/templates/groups.html`) is wired up by `initGroupMatchesToggle` in `app/web/static/js/app.js`, which flips every `.group-matches[open]` state and the button's label/`aria-expanded` together. It tracks state from the button's own `aria-expanded` attribute rather than inspecting each `<details>`, so it won't notice if a user manually expands/collapses one group by hand — acceptable for a convenience toggle, but worth knowing if you extend it.
- **Theme colors**: dark/light palettes are CSS custom properties on `:root`/`[data-theme="dark"]` and `[data-theme="light"]` in `app/web/static/css/style.css` (`--bg`, `--bg-elevated`, `--bg-elevated-2`, `--text`, `--text-muted`, `--border`, `--accent`, `--accent-hover`, `--accent-contrast`, `--accent-2`/`--accent-2-contrast` for the score pill, `--link`, `--table-stripe`, `--shadow`/`--shadow-sm`). Add new colors as variables in both blocks rather than hardcoding hex values in component rules, so the theme toggle (`app/web/static/js/app.js`, `data-theme` attribute) keeps working for every element.
- **Knockout bracket**: `/knockout` renders a graphical single-elimination bracket (`.bracket`/`.bracket-round`/`.bracket-pair`/`.bracket-match` in `app/web/static/css/style.css`) above the existing round-by-round detail tables — both read from the same `services.KnockoutStage(tournament)` result, so don't let them drift out of sync. `handlers.PageHandlers.Knockout` (`app/internal/handlers/pages.go`) splits that result via `splitThirdPlaceRound` into `BracketRounds` (the single-elimination tree only) and `ThirdPlace` (the "Match for third place" fixture, rendered as its own standalone `.bracket-third-place` box since it isn't part of the tree). The `pairs` template func (`app/internal/handlers/render.go`) groups a round's matches two at a time so each pair renders as one bracket "elbow" feeding into the next round; this assumes matches within a round are already in bracket order (true of `KnockoutStage`'s output). The winning team in each `.bracket-match` is highlighted via `{{if eq .Winner .Team1}}` — `models.Match.Winner()` (`app/internal/models/models.go`) accounts for extra time and penalty shoot-outs, not just the full-time score, specifically so this highlight is correct for knockout matches. Bracket scores use `{{with .FinalScore}}`. Undecided knockout slots use placeholders (`W74`, `2A`, ...); `MatchFilterOptions` filters them out of the team dropdown by keeping only names present in `Tournament.Teams`.
- **Matches filtering**: `/matches` accepts optional `round`, `group`, and `team` query parameters (combinable, case-insensitive, each matching either side of the fixture for `team`). `services.FilterMatches` (`app/internal/services/matches.go`) does the filtering — pure, no I/O — and `services.MatchFilterOptions` returns the distinct round/group/team values (schedule order for rounds, alphabetical for groups/teams) used to populate the `<select>` dropdowns in `app/web/templates/matches.html`'s filter form. The handler (`app/internal/handlers/pages.go`) only reads `r.URL.Query()` and wires the result into `matchesData`; it doesn't filter anything itself.

## Testing

- `app/internal/models`: `models_test.go` covers pure `Match` methods (`Winner()`, `FinalScore()`, including extra-time and penalty-shoot-out cases) with hand-built `Match` values.
- `app/internal/config`: `config_test.go` covers defaults, env overrides, and invalid `FETCH_TIMEOUT`/`LOG_FORMAT` fallback (uses `t.Setenv`).
- `app/internal/telemetry`: logger trace-ID injection (JSON/text) and `Enabled()`/`Setup` behavior for the `OTEL_*` variables. `handlers/health_test.go` covers `/readyz` draining, the incoming `traceparent` reaching the access log, and OpenMetrics exemplars (it sets the global W3C propagator, as `telemetry.Setup` does in production).
- `regression_test.go` (in `services` and `handlers`) pins previously fixed bugs. A new regression test should fail against the pre-fix code — check that it isn't vacuous (e.g. a page-level assertion that passes anyway because the data never reaches the page).
- `app/internal/data`: parser tests (`parser_test.go`) validate JSON normalization edge cases; store tests (`store_test.go`) validate refresh success/failure behavior using `httptest`.
- `app/internal/services`: table-driven tests with hand-built `models.Tournament` fixtures — no need to hit the real data source.
- `app/internal/handlers`: integration tests spin up the real router (`handlers.NewRouter`) against a store seeded from the embedded fallback, and assert on rendered HTML via `httptest`. These are markup/content regression checks (e.g. a specific button `id`, a specific CSS class, a specific fifa.com URL fragment) — there's no headless browser in the test suite, so CSS layout and JS behavior (button clicks, `<details>` toggling) still need manual verification in an actual browser (as documented under `/verify` or `/run` if available) when you touch `app/web/static/css/style.css` or `app/web/static/js/app.js`.
- Run `make test` or `make test-coverage`.

## Versioning

- The root `VERSION` file (plain semver text, e.g. `1.4.0`, no `v` prefix, no trailing newline) is the single source of truth for the app's release version. `Makefile` reads it into `APP_VERSION := $(shell cat $(VERSION_FILE) ...)` and derives `DOCKER_TAG`'s default from it — don't hardcode a version elsewhere (Docker tags, the Helm chart's `appVersion`) when it should instead flow from this file. Bumping it is a manual step (see `CONTRIBUTING.md`); nothing bumps it automatically.

## Docker

- `Dockerfile` is a multi-stage build: a `golang:1.27-alpine` builder pinned to `--platform=$BUILDPLATFORM` (native speed; cross-compiles via `TARGETOS`/`TARGETARCH`, `GOTOOLCHAIN=local`) produces a static binary run on a `distroless/static-debian13:nonroot` image (no shell). The image declares its own `HEALTHCHECK`. The Docker healthcheck relies on `app/cmd/server`'s `-healthcheck` flag (a local `GET /healthz`), since there's no `curl`/`wget` in the runtime image — keep that flag working if you touch `main.go`. Because the binary is `CGO_ENABLED=0` and statically linked, the same `Dockerfile` cross-compiles cleanly for both `linux/amd64` and `linux/arm64` with no per-arch branching needed.
- The runtime stage takes an `APP_VERSION` build-arg (default `dev`) and sets it as the `org.opencontainers.image.version` image label. It is **not** read from the `VERSION` file inside the Dockerfile itself — the runtime stage has no shell — it's passed in from outside via `--build-arg`; see below for who passes it.
- `make docker-build` / `make docker-up` wrap `docker compose build` / `up`, exporting `APP_VERSION=$(APP_VERSION)` (from the root `VERSION` file) so `docker-compose.yml`'s `build.args.APP_VERSION` and `image: my-world-cup-app:${APP_VERSION:-latest}` pick it up; `make docker-down` / `docker-logs` need no version. These wrap the default `docker` driver (single-arch, matches the local host) — for local dev only.
- **Multi-arch builds**: `make docker-buildx-setup` creates/reuses a `docker-container`-driver Buildx builder (`$(APP_NAME)-builder`) — the default `docker` driver can't produce multi-platform output. `make docker-build-multiarch` builds for `linux/amd64,linux/arm64` (override via `DOCKER_PLATFORMS`), tagged `$(APP_NAME):$(DOCKER_TAG)` (`DOCKER_TAG` defaults to the `VERSION` file's content), without pushing — purely to validate both platforms compile; Buildx can't `--load` a multi-platform result into the local daemon, so nothing is imported locally. `make docker-push` does the real publish: it first runs `helm-sync-version` (below), then interactively prompts for registry username, password/token (hidden input via `read -s`, piped to `docker login --password-stdin` — never a CLI arg or left in shell history), a repository name, and an optional tag (defaults to the `VERSION` file's content, not `latest`), infers the registry host to log into from the repository name's first path segment (falls back to Docker Hub if that segment has no `.`/`:`), then runs `docker buildx build --build-arg APP_VERSION=$$TAG --platform ... --push`. Keep these targets and their `## ` help text in sync with `README.md`'s Makefile Targets table per the convention above.

## Observability stack

- `docker-compose.observability.yml` is an **override** of `docker-compose.yml` (always used as `-f docker-compose.yml -f docker-compose.observability.yml`, via `$(OBS_COMPOSE)` in the Makefile), so relative paths inside it resolve from the repo root; configs live in `observability/` (`alloy/config.alloy`, `prometheus/prometheus.yml`, `loki/loki.yml`, `tempo/tempo.yml`, `grafana/provisioning/`, `grafana/dashboards/*.json`). Images are pinned to exact versions (Grafana, Prometheus, Loki, Tempo 3 in single-binary `-target=all` mode, Jaeger 2, Alloy); bump them together with README's stack table.
- Flow: Prometheus scrapes `app:8080/metrics` (OpenMetrics → exemplars, needs `--enable-feature=exemplar-storage`); Alloy receives OTLP from the app and fans traces out to Tempo **and** Jaeger, and tails container logs through the Docker socket (only containers of Compose project `my-world-cup-app` — hence `name:` in `docker-compose.yml`), promoting `level` to a Loki label and `trace_id`/`span_id` to structured metadata (never labels: high cardinality); Tempo's metrics generator remote-writes `traces_spanmetrics_*`/`traces_service_graph_*` to Prometheus. The app container's `logging.service_name` label makes its Loki `service_name` equal the traces' `service.name` (`my-world-cup-app`).
- Grafana data source UIDs are fixed (`prometheus`, `loki`, `tempo`, `jaeger`) and referenced by the dashboards and cross-links — don't rename them. In provisioning YAML, escape Grafana's own variables with a doubled dollar sign (e.g. `$${__trace.traceId}`), or Grafana's env-var expansion eats them.
- Jaeger ≥ 2.21 removed the legacy `/api/*` HTTP endpoints; Grafana needs `GF_FEATURE_TOGGLES_ENABLE=jaegerEnableGrpcEndpoint` to use `/api/v3`, and even then the bundled Jaeger plugin can only look traces up **by ID** (search still calls the removed endpoint) — so dashboards don't use Jaeger search panels; trace search goes through Tempo (TraceQL) or the Jaeger UI.
- Every published port binds to `127.0.0.1` (Grafana runs with anonymous Admin) and is overridable (`GRAFANA_PORT`, `PROMETHEUS_PORT`, `LOKI_PORT`, `TEMPO_PORT`, `JAEGER_PORT`, `ALLOY_PORT`).
- Dashboards are provisioned read-only (`allowUiUpdates: false`): edit the JSON files. Run `make observability-validate` (Compose merge, `alloy fmt`, `promtool check config`, `loki -verify-config`, `tempo -config.verify=true`, dashboard JSON/uid checks — each with the pinned image) after touching anything in `observability/`, and when you rename a log field, metric, or span, update the panels that query it. Panel queries can be smoke-tested against a running stack through Grafana's `/api/ds/query` (Tempo `serviceMap` queries run client-side only and can't be tested that way).

## Helm

- **Helm 4 only**: the chart targets Helm 4 (pinned in `mise.toml`); Helm 3 is no longer supported. `templates/_helpers.tpl`'s `my-world-cup-app.requireHelm4` (included at the top of `deployment.yaml`) `fail`s rendering when `.Capabilities.HelmVersion.Version` is `< 4.0.0`. Don't document Helm 3 commands/flags.
- `helm/my-world-cup-app` is a standard Helm chart (`Chart.yaml` `apiVersion: v2`, `values.yaml`, `templates/`). Probes: `startupProbe` and `livenessProbe` → `/healthz`, `readinessProbe` → `/readyz` (`periodSeconds` must stay below `env.SHUTDOWN_DRAIN_DELAY`, and `terminationGracePeriodSeconds` must exceed that delay + the app's 10s shutdown window); `env` sets `LOG_FORMAT=json` and `SHUTDOWN_DRAIN_DELAY=5s`, with commented `OTEL_*` examples; pod annotations pre-declare `prometheus.io/scrape|port|path` for `/metrics` auto-discovery. Pods run as UID/GID 65532 with `seccompProfile: RuntimeDefault`, and `serviceAccount.automountToken` defaults to `false`.
- Validate changes with `make helm-lint` (lints with default values and with `ingress.enabled`/`autoscaling.enabled` on) and `make helm-template` before committing.
- `helm/my-world-cup-app/README.md` is **generated, not hand-written** — it's produced by `make helm-docs` (wraps [helm-docs](https://github.com/norwoodj/helm-docs)) from `helm/my-world-cup-app/README.md.gotmpl` plus the `# -- description` head-comments in `values.yaml`. If you add/rename/remove a `values.yaml` key, add a matching `# -- ...` comment directly above it and re-run `make helm-docs` rather than editing the chart's `README.md` by hand.
- `helm/my-world-cup-app/Chart.yaml`'s `appVersion` (the app version the chart deploys) is **not** hand-edited either — `make helm-sync-version` overwrites it from the root `VERSION` file via a portable `sed -i.bak ... && rm -f *.bak` (works on both GNU sed/Linux and BSD sed/macOS). Both `make docker-push` and `make helm-docs` depend on it, so `appVersion` can't go stale before an image publish or a docs regeneration; `Chart.yaml`'s own chart `version` field (the chart's own release number, independent of the app version) is still bumped by hand.
- `make helm-install` / `make helm-uninstall` wrap `helm upgrade --install` / `helm uninstall` against the `NAMESPACE` variable (defaults to the app name).

## Common Pitfalls

- `go:embed` patterns cannot use `..` — this is why templates/static assets live under `app/web/` with their own `embed.go` (`app/web/assets.go`), rather than being embedded directly from `app/internal/handlers`.
- The openfootball match JSON omits the `score` field entirely for matches not yet played; `models.Match.Played()` checks `FullTime != nil`, not an empty score — don't assume `score.ft` is always present.
- Group standings tie-break is simplified (points → goal difference → goals for → alphabetical) and does **not** implement FIFA's head-to-head rule. This is documented in the UI and README; if implementing full tie-break rules, update both.
- A grid item's default `min-width` is `auto` (content-based), not `0` — a wide `.table` inside a `.card` inside a CSS grid track can blow out the whole page horizontally instead of scrolling inside its own `.table-responsive`. `.card` sets `min-width: 0` for this reason; keep that if you touch `.card`.
- `grid-template-columns: repeat(auto-fill, minmax(Npx, 1fr))` has a hidden phone-width bug: `auto-fill`/`auto-fit` reduce the column *count* when space is tight, but never shrink the `minmax` minimum itself — so a single column on a narrow viewport is still forced to be at least `Npx` wide, overflowing the page. Always wrap the minimum as `minmax(min(Npx, 100%), 1fr)` (see `.group-grid`/`.home-grid` in `app/web/static/css/style.css`).
